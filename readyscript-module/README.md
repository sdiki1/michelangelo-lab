# ReadyScript-модуль `michelangelo`

Модуль сохраняет проверенный идентификатор покупателя из Telegram или MAX
непосредственно в заказе ReadyScript. Внешний Python-сервис затем забирает
заказы обычным polling через `order.getList` / `order.get`.

## Поля заказа

Модуль добавляет в `shop_order`:

| Поле | Назначение | Внешний API |
|---|---|---|
| `telegram_user_id` | ID пользователя Telegram | да |
| `max_user_id` | ID пользователя MAX | да |
| `ml_bind_source` | `miniapp_verified`, `legacy` или ручная привязка | да |

Поля независимы: схема не теряет данные, даже если заказ вручную связан с обоими
мессенджерами. Polling-клиент использует Telegram в качестве приоритета только
пока локальная модель заказа поддерживает одну активную платформу.

Старые `ml_platform` / `ml_platform_user_id` остаются скрытыми для совместимости.
При обновлении модуля их значения переносятся в новые поля.

## Как возникает привязка

1. Витрина открывается как мини-приложение.
2. JS отправляет в `/michelangelo/track/` подписанный `initData`.
3. ReadyScript проверяет HMAC локально с токеном соответствующего бота.
4. Проверенный ID хранится в PHP-сессии.
5. При создании заказа ID записывается в `telegram_user_id` или `max_user_id`.

Заявленный браузером ID без корректной подписи никогда не записывается.

## Установка и обновление

1. Скопировать каталог `michelangelo` в `/modules` коробки ReadyScript.
2. В ReadyScript установить модуль или запустить его обновление, если была
   установлена версия 1.x. Установщик синхронизирует поля `shop_order` и выполнит
   перенос старых привязок.
3. В настройках модуля указать `telegram_bot_token` и `max_bot_token`.
4. Очистить системный кэш ReadyScript.
5. В настройках модуля «Внешнее API» разрешить методы `order.getList`,
   `order.get` и `oauth.token` для приложения polling-скрипта.

Не подключайте Telegram и MAX SDK синхронными тегами `<script>` в теме сайта.
Модуль сразу читает `tgWebAppData` / `WebAppData` из URL fragment и отправляет
подписанные данные в ReadyScript. После полной загрузки страницы он асинхронно
подключает только SDK фактического мессенджера. Если CDN второго мессенджера
недоступен, это не задерживает открытие витрины.

Сигнал готовности WebApp отправляется нативному мосту сразу, до загрузки SDK.
Поэтому экран загрузки Telegram или MAX не должен зависеть от доступности
`telegram.org` либо `st.max.ru`.

## Проверка

После открытия витрины из мини-приложения:

1. `POST /michelangelo/track/` должен вернуть JSON `{"ok": true, ...}`;
2. новый заказ должен содержать только поле своей платформы;
3. `order.get?order_id=<id>` должен вернуть `telegram_user_id` и
   `max_user_id` (пустое поле может отсутствовать в JSON);
4. polling-сервис запускается командой:

   ```bash
   michelangelo-readyscript-sync --loop --interval 60
   ```

Если новые поля не видны в API, обновите модуль ещё раз, очистите кэш и проверьте
параметр `appVisible` в справке `/api-<ключ>/help/`.

### Быстрая диагностика

- `/modules/michelangelo/view/js/miniapp-2.2.1.js` должен отвечать HTTP 200;
- `POST /michelangelo/track/` с пустым/неверным `init_data` должен отвечать JSON
  с HTTP 422, но не HTML-ошибкой 503;
- настройки JS в ReadyScript 6 находятся в `window.global.michelangeloIdentity`.

Для подробной трассировки включите настройку **«Диагностический журнал
привязки»**, откройте магазин из мессенджера и создайте новый заказ. Затем на
сервере выполните:

```bash
tail -n 200 /path/to/readyscript/storage/logs/michelangelo.log
```

Нормальная цепочка Telegram выглядит так:

```text
track.received
track.accepted
order.before
order.identity_stamped
order.after
```

Для фактической платформы модуль подключает официальный SDK асинхронно после
события `window.load`; SDK другого мессенджера не загружается. Кнопка магазина
в сообщении Telegram-бота должна быть кнопкой типа `web_app`, а не обычной
URL-кнопкой. Обычная ссылка, даже открытая внутри встроенного браузера
Telegram, не получает `initData`.

Расшифровка проблем:

- только `browser.probe` — браузер не предоставил `initData`, обычно магазин
  открыт обычной ссылкой или на неверном домене;
- `track.rejected` — неверный/пустой токен бота, устаревший либо повреждённый
  `initData`; поле `verify_error` уточняет причину (`hash_mismatch`, `expired`,
  `missing_user` и т.д.);
- есть `track.accepted`, но у `order.before` другая метка `session` — потеряна
  PHP-cookie, заказ оформляется на другом домене или через другой backend;
- `order.before` содержит `identity_present=0` — в сессии заказа нет identity;
- есть `order.identity_stamped`, но `order.after` пустой — проблема записи поля
  в БД; повторно обновите модуль и структуру базы;
- нет событий `order.*` — модуль не активен для сайта, на котором создаётся
  заказ, либо не очищен кэш обработчиков.

Журнал маскирует ID и не записывает токены или полный `initData`. Запись
выполняется без ожидания файловой блокировки, а обычный браузер не отправляет
диагностический POST. После диагностики выключите настройку.
